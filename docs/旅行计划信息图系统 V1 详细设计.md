# 旅行计划信息图系统 V1 详细设计

本设计以最终自动生成类似示例图片的旅行计划页面为目标。最终交付物包括：

* 可浏览的 HTML 旅行计划；
* 每日信息图页面；
* 可下载的 PNG 长图；
* 可保存或打印的 PDF；
* 注册用户空间中的历史版本。

全链路不需要人工介入：

```text
用户提交旅行诉求
→ 后端标准化
→ 大模型生成结构化旅行计划
→ 程序校验并自动修复
→ 展示编排器生成素材需求
→ 素材服务自动获取图片、图标和地图
→ 生成展示 ViewModel
→ React 模板渲染 HTML
→ Playwright 导出 PNG/PDF
→ 自动展示给用户
```

---

# 一、V1 范围定义

## 1.1 V1 支持范围

第一版建议支持：

| 项目     | V1 方案                   |
| ------ | ----------------------- |
| 行程天数   | 1～14 天                  |
| 输出语言   | 中文                      |
| 计划页面   | 响应式完整计划页                |
| 信息图    | 每日一张信息图                 |
| 模板     | `travel_infographic_v1` |
| Hero 图 | AI 插画或预制素材              |
| 景点图片   | 平台素材库优先，AI 兜底           |
| 美食图片   | 平台素材库优先，AI 兜底           |
| 图标     | 本地 SVG                  |
| 路线图    | 程序生成 SVG                |
| HTML   | React 模板生成              |
| 导出     | PNG、PDF                 |
| 历史计划   | PostgreSQL + pgvector   |
| 生成任务   | Redis 队列 + Worker       |
| 用户数据   | PostgreSQL              |
| 文件     | S3 兼容对象存储               |

## 1.2 V1 不支持范围

暂不处理：

* 航班和酒店实时库存；
* 自动下单；
* 商家点评聚合；
* 多人实时协同；
* 用户自由设计页面布局；
* 模型动态生成 React 代码；
* 模型直接写数据库；
* 模型直接生成最终 HTML；
* 复杂地理导航；
* 大规模公共社区图库。

# 三、核心服务拆分

## 3.1 Travel Request Service

职责：

* 接收前端提交的旅行诉求；
* 保存原始请求；
* 标准化标签；
* 计算人数、天数和预算；
* 检查输入冲突；
* 生成 `NormalizedTravelRequest`。

不调用图片服务，也不负责页面渲染。

---

## 3.2 Generation Orchestrator

这是整个流程的核心编排器。

职责：

1. 加载标准化旅行需求；
2. 检索历史计划；
3. 加载已验证的目的地资料；
4. 调用大模型生成 `TravelPlan`；
5. 执行 JSON Schema 校验；
6. 执行业务规则校验；
7. 自动修复违规项；
8. 保存有效计划版本；
9. 触发展示编排任务；
10. 触发渲染和导出任务。

---

## 3.3 Presentation Planner

展示编排器负责把完整旅行计划转换为“适合模板展示的数据”。

它不负责查找图片，只负责回答：

* 当前页面需要哪些模块；
* 每个模块显示多少条内容；
* 哪些文字需要压缩；
* 哪些素材槽位需要被填充；
* 使用哪一种模板和版式。

例如：

```json
{
  "template_id": "travel_infographic_v1",
  "page_type": "DAILY_POSTER",
  "day_number": 3,
  "content_limits": {
    "title_max_chars": 18,
    "subtitle_max_chars": 32,
    "schedule_max_items": 3,
    "food_max_items": 3,
    "photo_spot_max_items": 3,
    "ticket_max_items": 4,
    "booking_tip_max_items": 4
  },
  "asset_requirements": []
}
```

---

## 3.4 Asset Service

负责：

* 接收素材需求；
* 根据素材类型选择数据来源；
* 检索本地素材库；
* 调用授权图片源；
* 必要时调用 AI 图片模型；
* 生成地图 SVG；
* 返回统一格式的素材信息；
* 缓存和复用素材；
* 保存来源与版权信息。

---

## 3.5 Render Service

负责：

* 加载 `TravelPosterViewModel`；
* 使用 React 模板生成 HTML；
* 检查图片和字体加载；
* 检测页面溢出；
* 生成 PNG；
* 生成 PDF；
* 上传到对象存储；
* 返回访问 URL。

# 九、素材来源决策规则

## 9.1 图标

固定规则：

```text
ICON
→ 本地 SVG 图标库
```

不调用图片模型。

例如：

```text
/icons/travel/calendar.svg
/icons/travel/food.svg
/icons/travel/map.svg
/icons/travel/camera.svg
/icons/travel/ticket.svg
/icons/travel/transport.svg
/icons/travel/budget.svg
/icons/travel/tips.svg
```

---

## 9.2 路线地图

固定规则：

```text
ROUTE_MAP
→ SVG Map Renderer
→ 失败时显示路线列表
```

不调用图片模型。

---

## 9.3 Hero 图

推荐规则：

```text
预制城市主题图
→ 相似主题缓存图
→ AI 实时生成
→ 默认渐变背景
```

Hero 图可以使用 AI，因为它表达的是氛围和主题，而不是精确导航信息。

---

## 9.4 景点图片

推荐规则：

```text
平台已审核素材
→ 授权图片源
→ AI 风格化代表图
→ 默认景点占位图
```

AI 生成的景点图片必须标记：

```json
{
  "source_type": "AI_GENERATED",
  "representation_type": "ILLUSTRATIVE"
}
```

不能在后台把 AI 图当作真实照片使用。

---

## 9.5 美食图片

推荐规则：

```text
平台美食图库
→ 授权图片源
→ AI 生成美食图
→ 默认美食占位图
```

美食图片的真实性要求通常低于具体建筑照片，因此更适合作为 AI 兜底。

# 十、素材匹配评分

从素材库检索图片时，可以使用综合评分：

```text
final_score =
    实体名称匹配 × 0.35
  + 目的地匹配 × 0.20
  + 语义相似度 × 0.20
  + 画面比例匹配 × 0.10
  + 分辨率评分 × 0.05
  + 素材质量评分 × 0.05
  + 使用许可评分 × 0.05
```

伪代码：

```python
def score_asset(requirement, asset) -> float:
    return (
        entity_match(requirement, asset) * 0.35
        + destination_match(requirement, asset) * 0.20
        + semantic_similarity(requirement, asset) * 0.20
        + aspect_ratio_score(requirement, asset) * 0.10
        + resolution_score(requirement, asset) * 0.05
        + quality_score(asset) * 0.05
        + license_score(asset) * 0.05
    )
```

低于最低阈值时不使用。

例如：

```text
score >= 0.80：直接使用
0.65～0.79：可用，但优先继续查找
< 0.65：不使用，进入下一层兜底
```

# 十一、AI 图片生成规则

## 11.1 输入

图片模型接收的不是整个旅行计划，而是标准化的视觉 Brief：

```json
{
  "task": "GENERATE_TRAVEL_HERO",
  "destination": "杭州",
  "theme": "运河人文·古今交融",
  "elements": [
    "江南石桥",
    "运河游船",
    "现代博物馆",
    "临水历史街区"
  ],
  "style": "Chinese travel editorial illustration",
  "palette": [
    "fresh green",
    "warm gold",
    "soft blue"
  ],
  "layout": {
    "reserved_text_area": "LEFT_TOP",
    "subject_area": "RIGHT_AND_BOTTOM",
    "aspect_ratio": "16:6"
  },
  "negative_requirements": [
    "no text",
    "no logo",
    "no watermark",
    "no malformed buildings",
    "no excessive people"
  ]
}
```

## 11.2 生成后处理

AI 图片生成完成后要自动执行：

1. 检查文件是否有效；
2. 检查分辨率；
3. 检查长宽比；
4. 转为 WebP；
5. 生成缩略图；
6. 上传对象存储；
7. 写入素材表；
8. 记录生成参数和模型版本；
9. 缓存并复用。

## 11.3 不允许的做法

* 不让 AI 在图片里绘制标题；
* 不让 AI 绘制门票价格；
* 不让 AI 绘制地图文字；
* 不让 AI 生成带品牌 Logo 的图片；
* 不把 AI 景点图标记成真实照片。

# 十六、任务状态机

```text
QUEUED
NORMALIZING
VALIDATING_REQUEST
RETRIEVING_REFERENCES
GENERATING_PLAN
VALIDATING_PLAN
REPAIRING_PLAN
SAVING_PLAN
BUILDING_PRESENTATION
RESOLVING_ASSETS
GENERATING_ASSETS
RENDERING_HTML
EXPORTING_PNG
EXPORTING_PDF
COMPLETED
FAILED
```

素材相关错误不一定导致整个计划失败。

例如：

```text
Hero 生成失败
→ 使用默认主题背景
→ 任务继续

景点图缺失
→ 使用默认景点卡片
→ 任务继续

路线 SVG 失败
→ 使用文字路线列表
→ 任务继续
```

只有以下错误应阻断任务：

* 完整旅行计划不符合 Schema；
* 硬约束无法满足；
* 页面核心结构无法生成；
* HTML 模板渲染失败；
* 数据库写入失败。

# 十七、渲染流程

## 17.1 React 路由

```text
/render/plans/{plan_version_id}/days/{day_number}
```

该路由只供内部渲染服务访问。

## 17.2 页面就绪标识

React 页面加载完数据、图片和字体后设置：

```html
<body data-render-status="ready">
```

渲染 Worker 等待：

```javascript
await page.waitForSelector(
  '[data-render-status="ready"]'
);
```

## 17.3 页面检查

导出前执行：

```javascript
const result = await page.evaluate(() => {
  const overflowElements = [...document.querySelectorAll("*")]
    .filter(element =>
      element.scrollWidth > element.clientWidth ||
      element.scrollHeight > element.clientHeight
    );

  return {
    overflowCount: overflowElements.length,
    documentWidth: document.documentElement.scrollWidth,
    documentHeight: document.documentElement.scrollHeight
  };
});
```

检测到核心元素溢出时：

1. 切换压缩版文案；
2. 隐藏低优先级内容；
3. 改用宽松模板；
4. 再次渲染。

# 十八、自动降级策略

| 失败项目   | 第一兜底      | 第二兜底         |
| ------ | --------- | ------------ |
| Hero 图 | 已缓存的城市图   | 渐变背景         |
| 景点图片   | AI 风格化插画  | 默认景点占位图      |
| 美食图片   | AI 美食图    | 默认美食图        |
| 路线地图   | 简化 SVG    | 纯文字路线        |
| 图标     | 默认 SVG 图标 | Unicode 符号   |
| 文案过长   | 自动压缩      | 减少条目         |
| PDF 失败 | 重试一次      | 仅提供 HTML/PNG |
| PNG 失败 | 重试一次      | 仅提供 HTML/PDF |

# 十九、缓存策略

## Hero 图缓存键

```text
destination
+ theme
+ visual_style
+ aspect_ratio
```

例如：

```text
hangzhou
+ canal_culture
+ chinese_editorial
+ 16x6
```

同类计划可以复用相同 Hero，不必每次实时生成。

## 景点图缓存键

```text
place_id + image_role + aspect_ratio
```

## 美食图缓存键

```text
dish_name + city + visual_style
```

## 地图缓存键

```text
route_node_hash + map_style
```

这样可以显著降低延迟和成本。

# 二十、安全和合规

## 图片来源必须记录

每个素材至少记录：

```text
source_type
license_type
original_url
attribution_text
generated_model
generated_at
```

## 用户侧展示

AI 生成的氛围图不必在页面显著标注，但后台必须可追踪。

AI 生成的具体景点代表图，建议在详细信息中显示：

```text
示意图
```

## 外部图片

外部图片应下载、审核并转存到自己的对象存储，不建议页面直接引用第三方地址。

原因包括：

* 防止图片失效；
* 防止防盗链；
* 确保 PDF 可导出；
* 控制图片格式和尺寸；
* 保存版权信息。

# 二十四、V1 验收标准

满足以下条件即可进入内测：

1. 用户提交表单后无需人工处理；
2. 模型输出能够自动保存到数据库；
3. 计划必须经过 Schema 和业务规则校验；
4. 每日都能生成一个信息图 ViewModel；
5. 图标加载成功率为 100%；
6. 路线图失败时能自动降级；
7. Hero 图失败时仍能生成页面；
8. 景点和美食图片缺失时不阻断流程；
9. 页面不存在文字遮挡和明显溢出；
10. HTML、PNG、PDF 至少两种输出可用；
11. 用户只能访问自己的私有计划；
12. 所有素材均可追踪来源；
13. 相同任务不会重复生成；
14. 生成失败有明确错误码和重试机制；
15. 不向用户展示未通过校验的模型草稿。

# 二十五、V1 最终链路

```text
TravelRequestUI
    ↓
NormalizedTravelRequest
    ↓
历史计划与资料检索
    ↓
大模型生成 TravelPlan
    ↓
Schema 校验
    ↓
业务规则校验
    ↓
自动修复
    ↓
保存 TravelPlanVersion
    ↓
Presentation Planner
    ↓
AssetRequirement
    ↓
Asset Resolver
    ├── 本地图标
    ├── 路线 SVG
    ├── 素材图库
    ├── AI 图片生成
    └── 默认兜底
    ↓
TravelPosterViewModel
    ↓
React 模板
    ↓
HTML
    ↓
Playwright
    ├── PNG
    └── PDF
    ↓
对象存储
    ↓
前端展示结果
```

这版设计的核心边界是：

> **大模型决定“旅行内容是什么”，展示编排器决定“页面需要展示什么”，素材服务决定“图片和视觉素材从哪里来”，React 模板决定“最终页面长什么样”。**

四个部分相互独立，后续更换大模型、增加图库、增加模板或替换图片生成服务时，都不需要推翻整套系统。
